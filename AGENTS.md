# Sistema Almacén — Las Flores

Aplicación web de control de inventario para el almacén de Restaurante Las Flores.
Stack: **React 19 + Vite + Tailwind CSS v4 + Supabase**. Desplegada en **Vercel**.

## Servidor de desarrollo

```bash
pnpm install
pnpm dev          # Vite en el puerto $PORT (por defecto 8443), con hot reload
pnpm run build    # compilación de producción a dist/
pnpm run preview  # sirve la compilación de dist/
```

## Estructura del proyecto

- `src/main.tsx` — punto de entrada; monta `src/App.tsx` dentro de `ToastProvider`
- `src/App.tsx` — componente raíz: autenticación con Supabase, sidebar responsive y enrutado entre pantallas. Deriva la `cuenta` activa (marca del panel: logo + nombre) del correo de la sesión vía `cuentaPorEmail`, no de lo que se eligió en el login, así es correcta también tras recargar la página. Si `cuenta.esAdmin` es verdadero y no se está "impersonando" ningún almacén (`verComoAlmacen === null`), renderiza `AdminDashboard` en vez del shell normal; al elegir un almacén ahí (`onEntrar`), `verComoAlmacen` pasa a ser esa clave y el resto de la app (sidebar, `StoreProvider`, `PageContent`) usa `almacenActivo`/`cuentaActiva` en vez de `cuenta`/`cuenta.almacen` directamente — es impersonación por estado de React, la sesión real (y el permiso RLS de fondo) siguen siendo los del Administrador. El widget de cuenta del sidebar suma "Volver al panel de Administrador" solo mientras se está impersonando.
- `src/components/` — pantallas y formularios:
  - `Registrar` (`Nuevo producto` en el menú) → `NewProductEntryForm`: alta de un producto en ESTE almacén. El código YA NO es lo que detecta duplicados (cada almacén tiene su propia numeración independiente, ver `producto_codigos` en `store.tsx` más abajo — que Umaru y Las Flores usen el mismo número no significa nada). En su lugar, mientras se escribe la descripción se busca por NOMBRE en `catalogoMaestro` (client-side, reusa `filtrarBusqueda`) y se muestran hasta 5 sugerencias con botón "Sí, es este"; la persona decide, nunca se fusiona nada automático por coincidencia de texto (fusionar mal dos productos distintos, o no fusionar dos que sí son el mismo por una tilde de más, es peor que pedir un clic). Si confirma una sugerencia (`match`), Descripción/Unidad/Categoría/Imagen se bloquean con los datos del catálogo maestro (no se puede hacer que "el mismo producto" tenga dos identidades), quedan editables Cantidad inicial/Costo/Stock mínimo/Fecha/Área/Código (100% de este almacén) y el botón dice "Agregar a mi almacén". Al enviar, `registrarProductoEnAlmacen({ codigo, productoId })` o `registrarProductoEnAlmacen({ codigo, nuevo: {...} })` (del store) resuelve si hace falta crear identidad nueva en el catálogo maestro o solo mi código local — ver el detalle en `store.tsx` más abajo. Es el mismo espíritu "automático, sin crear a mano" que ya tenía la recepción de traspasos (ver `RecibirTraspasoModal` más abajo).
  - `Entries` / `Exits` (`Entradas` / `Salidas`): cada uno monta `MovementCart` (carrito multi-ítem: buscar producto → agregar → cantidad → responsable → registrar; en Salida además motivo + impresión del comprobante) y debajo el `MovementsTable` con el historial.
  - `MovementCart` — carrito de registro; `addMovements` del store escribe todos los movimientos en un solo `insert`. `Field` — helper de campo etiquetado.
  - `ImageUploadField` — campo de imagen de producto reutilizable (elegir archivo, arrastrar y soltar, o pegar con Ctrl+V); lo usan `NewProductEntryForm`, `EditProductModal` y `EditMovementModal`. Sube con `utils/storage.ts`.
  - `Comprobantes` (`Comprobantes` en el menú): lista la copia congelada de cada comprobante de **salida** impreso (tabla `comprobantes`, filtrada a `tipo = 'Salida'`); permite ver el detalle y **reimprimir**. `ComprobanteSalida` — el comprobante térmico en sí (portal + hook `usarImpresionComprobante`), compartido por el carrito de salida y la reimpresión.
  - Numeración (`calcularNumeros`, `proximoNumero`, `etiquetaComprobante` del store): entradas y salidas generan un `Comprobante` con número correlativo por tipo (`E-1` / `S-1`), uno por registro (las líneas de un carrito comparten número), reinicia cada año (`periodo`). El N° sale de la tabla `comprobantes` (creada en `supabase/migration-fase5.sql`) y es fijo aunque después se edite o borre un movimiento. La columna "N° de Entrada / N° de Salida" aparece en ambos historiales; la copia reimprimible del módulo Comprobantes es solo para salidas.
  - `Dashboard`, `Inventory`, `CodeSearch` (`Buscar producto`: ficha e historial de un producto), `ExportExcel`, `Configuracion`, los modales de edición, `ComboBox` (desplegable editable), `Pager` (paginación).
  - `Configuracion` (`Configuración`): usuario y almacén de la cuenta activa (`cuenta` prop, ver `App.tsx`) y **cierre de periodo** (cierre anual). Ya no tiene cambio de contraseña NI "Vaciar almacén" — las dos son del Administrador ahora (ver `AdminConfiguracion` más abajo, sección "Zona de peligro"); acá solo quedan notas indicando que hay que contactarlo. El Dashboard muestra un aviso no descartable cuando hay movimientos del año anterior sin cerrar.
  - `Traspasos` (`Traspasos` en el menú, recibe `cuenta` igual que `Configuracion`): envía y recibe mercadería entre almacenes. `NuevoTraspasoForm` — carrito (igual patrón que `MovementCart`) que descuenta MI stock al toque y crea un traspaso "pendiente" (`enviarTraspaso` del store); el selector de destino excluye cuentas con `esAdmin`. Antes de enviar, cada línea del carrito resuelve su `productoId` (identidad del catálogo maestro) buscando en mi propio `productos` por código — es la llave que el destino usa para identificar el producto, NO el código (que es local a mi almacén y puede no significar nada del otro lado). El número de traspaso (`T-1`, `T-2`…) es **global entre los dos almacenes**, no por almacén de origen — antes cada uno tenía su propio correlativo y podían coincidir dos "T-1" distintos en el mismo historial. Lo asigna el RPC `siguiente_numero_traspaso` (`supabase/migration-fase14.sql`, tabla `traspaso_contadores`), atómico (un `UPSERT` que Postgres serializa) porque calcularlo en el cliente no alcanza: ni es atómico (dos envíos casi simultáneos podrían calcular el mismo número) ni, con RLS, una cuenta puede ver todos los traspasos que existen (solo los suyos) para sacar un máximo global confiable. `enviarTraspaso` ahora devuelve `{ error, numero }` en vez de solo el mensaje de error — el número real asignado por la base, para que el comprobante impreso lo use directo en vez de volver a calcularlo del lado del cliente. `RecibirTraspasoModal` — **línea por línea**: cada ítem tiene un checkbox "aceptar" + cantidad a recibir + área destino (ya NO muestra el código de la línea — sería el código LOCAL del almacén de origen, no significa nada para quien recibe); como `productoId` ya es la identidad del catálogo maestro, aceptar una línea YA NO requiere buscar a qué producto propio corresponde ni crear uno nuevo — `recibirTraspaso` (en `store.tsx`) resuelve mi propio código local para ese `productoId` (reusa el que ya tenga, o le asigna el siguiente de mi secuencia) y arma el movimiento de Entrada solo, con descripción/unidad/costo/categoría tomados del snapshot que mandó el origen (`t.items`). Los destildados se rechazan solos, sin pedir motivo. `recibirTraspaso` restituye el stock de las líneas rechazadas vía el RPC `traspaso_restituir_rechazados` (`supabase/migration-fase11.sql`) — esos movimientos son del almacén de ORIGEN, RLS no deja tocarlos directo desde el destino, por eso la función privilegiada (mismo patrón que `admin_cambiar_password`); si no se acepta ninguna línea, delega en `cancelarTraspaso`. `cancelarTraspaso` sirve tanto para que origen cancele antes de que lo reciban como para que destino rechace todo con motivo — también usa esa función cuando quien cancela es el destino (el borrado directo por `.eq("almacen", almacen)` solo sirve si cancela el origen). `ComprobanteTraspaso`/`usarImpresionTraspaso` — mismo mecanismo de impresión que `ComprobanteSalida`, clonado (no generalizado); el ticket impreso nunca mostró código, solo descripción/cantidad/unidad, así que no lo afecta que el código ahora sea local. Es la única entidad de la app que un almacén ve sin ser dueño exclusivo de la fila — ver `supabase/migration-fase7.sql`.
  - `AdminDashboard` (pantalla propia, sin sidebar — es lo que ve la cuenta Administrador al entrar, antes de elegir un almacén): trae movimientos de LOS DOS almacenes con fetches directos a Supabase (`buildInventory`/`movementFromRow`, exportados de `store.tsx` para esto, sin pasar por `StoreProvider`) más los traspasos pendientes de cada uno, y muestra una tarjeta por almacén con sus KPIs de ESTADO ACTUAL nada más (productos, unidades, por reponer, sin stock, traspasos pendientes; el valor del inventario queda como dato secundario, no destacado) y un botón "Entrar al panel de…" (`onEntrar`, ver `App.tsx`). Ya no tiene "Entradas"/"Salidas" (conteo histórico sin rango) ni el botón de descargar PDF — eso se movió entero a `Reportes`, que lo hace mejor (con fecha, con detalle); acá solo queda lo que es genuinamente "ahora mismo", cosa que Reportes no cubre. Dos botones en el header (íconos, `vista` local) alternan a `Reportes` y `AdminConfiguracion` en vez de las tarjetas.
  - `Reportes`: rango de fechas (Desde/Hasta, con atajos Hoy/Esta semana/Este mes/Mes pasado/Este año) + selector de almacén (uno de los dos, o "Los dos almacenes" combinado) + buscador de **producto** opcional (por NOMBRE contra el catálogo maestro — ya no por código, cada almacén tiene el suyo — mismo patrón `filtrarBusqueda` que el resto de la app; sin elegir uno, el reporte es de todos) → tarjetas de Entradas, Salidas, Productos nuevos, Traspasos enviados y Traspasos recibidos, cada una con botón "Ver detalle" que abre la lista real de filas (modal paginado con `Pager`, mismo patrón que `Inventory`/`Traspasos`), más un botón "Descargar reporte" (jsPDF + `autoTable`, heredado de `AdminDashboard` pero armado de nuevo: exporta exactamente el rango/almacén/producto que están elegidos en pantalla, no una foto aparte del momento actual). Como `AdminConfiguracion`, no pasa por `StoreProvider`: trae el historial COMPLETO de `movements` de cada almacén (sin filtro de fecha) y de `traspasos` una sola vez al montar — todo el filtrado por rango/almacén/producto pasa después, client-side, vía `useMemo` (mismo patrón que `AdminDashboard` arma sus KPIs), así cambiar de fecha o de almacén en pantalla es instantáneo, sin ida y vuelta a la base. Aparte, fetchea el catálogo maestro COMPLETO (`productos`, sin código — solo para el buscador de producto) y `producto_codigos` COMPLETO (sin filtro de almacén, admin ve todo por RLS) una sola vez al montar: con eso arma `codigoPorAlmacenYProducto` (`${almacen}::${productoId}` → código), porque un producto elegido puede tener un código LOCAL distinto (o ninguno) en cada almacén — no hay un solo "código" comparable entre los dos. Los movimientos de cada almacén se filtran por SU PROPIO código resuelto ahí; los traspasos se filtran directo por `t.items.some((it) => it.productoId === productoId)` (más simple, no necesita resolver nada). "Productos nuevos" sigue siendo POR ALMACÉN: el primer movimiento real de cada código EN ESE almacén (mínimo `created_at` de `movements`, agrupado por código) que cae dentro del rango — si hay un producto elegido y ese almacén no tiene código local para él, no aporta nada (nunca lo tuvo).
  - `AdminConfiguracion`: lista los dos almacenes reales (`CUENTAS.filter(c => !c.esAdmin)`, no la propia cuenta del administrador — esa contraseña la cambia el equipo de desarrollo directo en Supabase) con, por fila, "Cambiar contraseña" (RPC `admin_cambiar_password`, `supabase/migration-fase10.sql` — el único lugar de toda la app donde se puede cambiar la contraseña de OTRA cuenta; `auth.updateUser()` no sirve para eso). No pasa por `StoreProvider` (acá no hay ninguno montado, como en el resto de `AdminDashboard`) así que llama a Supabase directo, apuntando al `almacen` de la fila. La sección "Zona de peligro" ya no tiene "Vaciar almacén" (esa acción se consideró redundante con el cierre de periodo, que ya vive en el `Configuracion` de cada almacenero) — solo queda `EliminarCatalogo`: borra TODA la tabla `productos` (catálogo maestro compartido, cada fila un producto real por `id` — afecta a los dos almacenes a la vez, no hay una versión "por almacén"), con conteo en vivo y una frase de confirmación exigente (`ELIMINAR CATALOGO`, no la misma que otras confirmaciones, para no confundirla). El borrado cascada a `producto_codigos` (`on delete cascade`, ver `migration-fase17.sql`) pero NO de ahí a `movements`: si algún almacén todavía referencia ese código (`movements_codigo_almacen_fkey`), Postgres rechaza el delete completo (atómico, sin borrado parcial) y el error se traduce a un mensaje claro en vez de dejarlo crudo.
- `src/store.tsx` — estado global y sincronización con Supabase; el inventario y las listas (categorías, áreas, unidades) se derivan de los movimientos; la carga pagina de a 1000 filas. `addMovement` (uno) y `addMovements` (lote, con validación de stock acumulada y rollback si falla el insert). `cerrarAnio(anio)` + `construirCierre(movements, anio)`: el cierre anual archiva los movimientos con fecha ≤ 31/12 del año y los reemplaza por un saldo inicial por producto (Entrada fechada el 01/01 del año siguiente, `responsable = "SALDO INICIAL AAAA"`); crea los saldos, verifica y borra los archivados en lotes; un reintento no vuelve a crear saldos. `StoreProvider` recibe `almacen` (de `App.tsx`, viene de la cuenta activa o, para el Administrador, del almacén que esté impersonando; también expuesto en `useStore()`) y lo usa en **todas** las consultas/escrituras (`.eq("almacen", almacen)`, y en el payload de `movementToRow`/`comprobanteToRow`) y en las claves de `localStorage`, para que cada cuenta solo vea y guarde sus propios datos — la separación real la hace RLS en la base (ver `supabase/migration-fase6.sql`), esto es la segunda capa del lado de la app. `enviarTraspaso`/`recibirTraspaso`/`cancelarTraspaso` arman sus propios movimientos "sueltos" (como los saldos de `cerrarAnio`, sin comprobante E-/S-) con verificación fuerte (`.select("id")`) antes de tocar la tabla `traspasos` — la única consulta del store que no es de un solo almacén (`fetchAllTraspasos`, con `.or(almacen_origen.eq...,almacen_destino.eq...)`). `buildInventory` y `movementFromRow` están `export`ados (además de su uso interno) para que `AdminDashboard` pueda calcular inventario de cualquier almacén desde filas crudas de Supabase, sin montar `StoreProvider`.
  **Catálogo maestro + código local por almacén** (`productos` + `producto_codigos`, tablas creadas en `supabase/migration-fase13.sql` y `migration-fase17.sql`): la identidad de producto (descripción, unidad, categoría, imagen) vive en `productos`, compartida entre TODOS los almacenes, identificada por `id` (uuid interno, invisible para el usuario) — se fetchea SIN `.eq("almacen", almacen)`, es la misma tabla para cualquier cuenta. El CÓDIGO que cada almacén ve/imprime/busca vive aparte, en `producto_codigos` (`almacen, producto_id, codigo`), independiente por almacén — Umaru y Las Flores pueden tener códigos distintos (o iguales por casualidad, da igual) para el mismo producto, y cada uno arranca su propia numeración en 1. Esto separa dos cosas que antes eran la misma columna (`productos.codigo` como PK compartida): antes, el correlativo de un almacén nuevo heredaba donde se había quedado el otro (Umaru nunca podía empezar en 1), y un producto creado independientemente en cada almacén quedaba como dos identidades sin relación (el traspaso entre ellas ya no habría sido automático). `useStore().productos` es MI PROPIA vista (join de mis `producto_codigos` con `productos` por id — mismo shape de siempre: `{id, codigo, descripcion, unidadMedida, categoria, imagen}`); `useStore().catalogoMaestro` es el catálogo completo de los dos almacenes, SIN código (`ProductoMaestro`), para buscar "¿ya existe esto?" por nombre (ver `NewProductEntryForm`). `movements.codigo` tiene FK COMPUESTA a `producto_codigos(almacen, codigo)` (`on update cascade`): todo movimiento tiene que referenciar un código que ya exista EN MI ALMACÉN. `nextCodigo()` calcula el correlativo sobre `productos` (que ya viene scopeado a mi almacén) — automáticamente per-almacén, sin lógica especial. `registrarProductoEnAlmacen({codigo, productoId})` o `registrarProductoEnAlmacen({codigo, nuevo})` (reemplaza a `crearProductoEnCatalogo`) da de alta un producto EN MI ALMACÉN: si `productoId` viene (la persona confirmó una sugerencia del catálogo maestro), solo inserta mi fila de `producto_codigos`; si viene `nuevo`, primero crea la identidad en `productos` y recién después mi código local, con rollback del maestro si el segundo insert falla (para no dejar una identidad húerfana). `updateProduct` (usa `EditProductModal`) separa las dos escrituras: descripción/unidad/categoría/imagen actualizan `productos` por `id` (compartido, afecta a los dos almacenes A PROPÓSITO — es la misma identidad); el código actualiza `producto_codigos` por `(almacen, codigo)` — renombrarlo ahora es 100% LOCAL, ya no cascadea al otro almacén como pasaba antes cuando el código era la PK compartida. `deleteProduct` borra `movements` de mi almacén y también libera mi fila de `producto_codigos` — el producto sigue existiendo en el catálogo maestro para el otro almacén.
  `buildInventory(movements)` — el inventario de un almacén es SOLO lo que tiene movimientos reales ahí, cada almacén es independiente (pedido explícito de Rio: reportes y KPIs no deben mezclar conteos de los dos almacenes). El catálogo maestro sigue siendo la identidad única entre almacenes para que el traspaso y el alta de un producto repetido funcionen sin crear nada a mano, pero NO se mezcla en el inventario — una versión anterior sí lo hacía (cualquier código del catálogo entraba con cantidad 0) y eso generó justo la confusión que se quería evitar: el panel de Administrador y los Reportes contaban "334 productos" en un almacén que en realidad tenía muchos menos.
- `src/utils/excel.ts` — `descargarHoja` (json → .xlsx de una hoja) y `movimientoAFila` (formato de fila compartido por Exportar Excel y el respaldo del cierre).
- `src/toast.tsx` — avisos en pantalla (`useToast`, `<ToastProvider>`)
- `src/supabaseClient.ts` — cliente de Supabase y `CUENTAS`: la lista de cuentas de acceso (usuario del login → email real de Supabase Auth → nombre, logo y **`almacen`** — la clave de aislamiento de datos de esa cuenta). Cada almacén tiene su propio inventario/movimientos/comprobantes/categorías, separados por Row Level Security: las políticas comparan `almacen` contra `public.almacen_actual()`, que lo lee del `app_metadata` del JWT de la sesión (no un mapeo de emails hardcodeado en la política — eso lo hace más fácil de escalar y evita que un typo en una política deje a una cuenta entera sin acceso a lo suyo). Agregar una cuenta nueva: sumar la entrada acá, crear el usuario en el Dashboard de Supabase, y correr un `update auth.users set raw_app_meta_data = … where email = …` (paso 4 de `migration-fase6.sql`) — las políticas RLS no cambian. La cuenta Administrador se marca con `esAdmin: true`: su `almacen` ("admin") nunca se usa para filtrar datos reales — en vez de `almacen_actual()`, sus políticas RLS pasan por `public.es_admin()` (lee `role` del `app_metadata`, ver `migration-fase9.sql`), un bypass que aplica a cualquier almacén. Ver README.
- `src/types.ts` — tipos (`Movement`, `InventoryItem`, `Traspaso`, `Producto` — mi código local + identidad, `ProductoMaestro` — catálogo compartido sin código, ver `store.tsx`), listas por defecto (`AREAS`, `DEFAULT_CATEGORIES`, `UNIDADES_MEDIDA`)
- `src/utils/image.ts` — redimensionado y compresión de imágenes de producto
- `src/utils/storage.ts` — sube la imagen comprimida a Supabase Storage (bucket `productos`); si falla usa un data URL
- `src/index.css` — CSS global: `@import 'tailwindcss'`, tokens de marca (`@theme`), controles base y reglas de impresión
- `index.html` — shell HTML de Vite; `site.config.json` complementa los metadatos vía `vite.config.ts`
- `supabase/schema.sql` — esquema completo (tablas, índices, RLS, bucket de Storage, semillas). `supabase/migration-*.sql` — migraciones incrementales para bases de versiones anteriores
- `scripts/import-almacen.mjs` — importador puntual del inventario desde el Excel de Rio; lee `doc/…​.xlsm` (no versionado) o `IMPORT_XLSX`. Modos `--dry-run` y `--sql`
- `vite.config.ts` — configuración de Vite (React, Tailwind v4, alias `@` → `src`)
- `.mise.toml` — versiones de Node.js y pnpm
- `.github/workflows/keepalive.yml` — cron diario que hace una consulta de solo lectura a Supabase para que el proyecto (plan gratuito) no se pause por 7 días de inactividad. Necesita los secrets `SUPABASE_URL` y `SUPABASE_ANON_KEY` en el repositorio.

## Estilos

**Tailwind CSS v4** vía el plugin `@tailwindcss/vite`. `src/index.css` importa Tailwind con
`@import 'tailwindcss';` y define los tokens de la marca en un bloque `@theme` (escala `brand-*`,
neutros cálidos, fuentes). Usar las utilidades de Tailwind directamente en el JSX y poner CSS global
o personalización del tema en `src/index.css`. No hace falta archivo de configuración de Tailwind ni
de PostCSS.

Las `@import` de CSS van primero, luego las reglas `@font-face` y los valores por defecto de fuente.

## Calidad de código

- Usar comillas dobles para cadenas con apóstrofes (`"We're here to help"`), o escaparlos en cadenas
  con comillas simples. Un apóstrofe sin escapar dentro de comillas simples rompe el build.
- Cerrar todas las etiquetas JSX y balancear las llaves.
- Exportar los componentes como export por defecto.
